# Integration Patterns: Lovable ↔ Supabase ↔ n8n

**Definition:** the ways a user action in the Lovable app can start an n8n workflow, and the ways results get back to the UI.

**Why it matters for us:** this is the seam where hackathon teams lose hours to CORS, 404 webhooks, RLS and leaked keys. We pick one pattern and stick to it. The decision is recorded in [[DEC-002 Backend and integration pattern (proposed)]].

## Trigger: app → n8n

### (a) App → Supabase insert → Database Webhook → n8n  ✅ recommended
```
Browser --insert (publishable key, RLS)--> call_requests --pg_net POST--> n8n /webhook/...
```
- **Pros:**
  - The browser never knows the n8n URL or any secret.
  - **No CORS** (the call is server-to-server).
  - The row exists *before* n8n runs, so the UI has an `id` to subscribe to immediately.
  - A single source of truth: failed runs are visible in the table (`status`).
  - It's easy to re-trigger (insert again, or call the webhook manually with the same payload).
  - Lovable is good at generating "insert into table X" code, which costs few credits.
- **Cons:**
  - One extra setup step (the DB webhook in the Supabase dashboard).
  - Debugging goes through `net._http_response` ([pg_net docs](https://supabase.com/docs/guides/database/extensions/pg_net)).
  - pg_net is fire-and-forget: if n8n is down, nothing retries automatically. That's acceptable for a demo; add a "Retry" button that resets `status='new'` via n8n, or re-insert.
- **Setup:** [[Supabase - Practical Guide#4. Database Webhooks → n8n (pg_net)]] + [[n8n - Practical Guide#2. Webhook node]] (Header Auth, Respond Immediately).

### (b) App → n8n webhook directly (fetch from browser)
- **Pros:** fastest to wire; one hop; n8n can respond with data synchronously.
- **Cons:**
  - **CORS**: you must set *Allowed Origins*, and the multi-origin bug ([#18528](https://github.com/n8n-io/n8n/issues/18528)) bites when preview and published origins differ.
  - The webhook URL and any header secret are **visible in the JS bundle**, so anyone can spam the workflow and burn executions and LLM tokens.
  - Browser timeouts on long LLM chains ([community](https://community.n8n.io/t/lovable-app-with-n8n-ai-workflow-webhook-timeout/133975)).
  - You still need to write to Supabase separately for the live view.
- **Use when:** a quick synchronous AI helper (e.g. "translate this sentence") where no DB row is needed. Set Allowed Origins to the single published origin and add a rate limit if possible.

### (c) App → Supabase Edge Function → n8n
- **Pros:** secrets stay server-side; you can validate input, write the row and call n8n in one place; no CORS problems toward n8n (though you handle CORS for the function itself).
- **Cons:**
  - More code, generated by Lovable (credits) or written by hand.
  - Deploying and debugging another runtime.
  - JWT and verify settings ([docs](https://supabase.com/docs/guides/functions/auth)).
  - It duplicates what (a) gives for free.
- **Use when:** we are stuck on **Lovable Cloud** (no secret key for n8n), or the trigger must do something synchronous before n8n runs, such as charging or validating against a third party.

### Pick for 48 h: **(a)**
It needs the least custom code, has no secrets in the frontend, avoids CORS, and gives a natural hook for the live view. Keep (b) as a fallback if the DB webhook misbehaves on Saturday. It's a 10-minute swap: change the Lovable form submit to `fetch(n8nUrl)`, and have n8n insert the row itself.

## Results: n8n → UI

### ✅ n8n (and the relay) write to Supabase → Realtime → UI
- n8n: **Supabase node → Update** `call_requests` (`status`, `brief_de`, `booked_slot`, `outcome`) with the secret key.
- Relay server: inserts `call_events` rows (transcript lines) **directly** into Supabase with the secret key, via supabase-js or REST. **Don't route each transcript line through n8n.** It adds latency, eats executions and n8n isn't made for streams.
- UI: loads the existing rows, then subscribes to `postgres_changes` on both tables, filtered by `request_id` ([Realtime docs](https://supabase.com/docs/guides/realtime/postgres-changes)).
- The English translation per line: the relay can call Claude per utterance and write `text_en` in the same insert, or n8n can fill `text_en` after the call. Start without it and add it if time allows.

### Alternatives (not recommended here)
- **Respond to Webhook with the result** (synchronous): only works with pattern (b), and only for fast workflows.
- **Polling** an n8n endpoint or table every few seconds: works everywhere, but looks laggy and costs requests. It's an OK emergency fallback if Realtime breaks (`setInterval` + `select`).

## Status state machine (shared contract)

```
new ──(WF1 picks up)──> briefing ──(brief ready, call started)──> calling ──> booked
                                                                        ├──> rejected
any ──(error)──> failed
```
Only the server side (n8n, relay) moves the status forward. The UI only inserts `new`. Write this contract into Lovable Knowledge and the n8n workflow descriptions.

## Vercel

- **Not needed for the core build.** Lovable hosts the frontend (`*.lovable.app` counts as the "own URL").
- Where it *could* help:
  1. **Fallback frontend host** if Lovable credits run out: sync to GitHub → import into Vercel (preset Vite, `npm run build`, output `dist`, `VITE_SUPABASE_*` env vars, SPA rewrite) ([Lovable docs](https://docs.lovable.dev/tips-tricks/external-deployment-hosting)). Keep editing with Claude Code for free.
  2. **Small serverless endpoints** (e.g. an `.ics` generator, a signed status page).
- **Not for the call relay:** Twilio Media Streams need a long-lived WebSocket server. Vercel Functions are request/response and aren't suited to hosting a WebSocket server (*from general knowledge; verify if considered*). Run the relay with **Docker** on a small VM, Railway, Render or Fly, or on a laptop behind a `cloudflared`/ngrok tunnel for the demo.

## Pitfall checklist (seams)

| Pitfall | Symptom | Fix |
|---|---|---|
| Test webhook URL used in the Supabase webhook or app | Works once in the editor, then 404 "not registered" | Use `/webhook/` (not `/webhook-test/`) and **Publish** → [[Rules/n8n - use production webhook URLs]] |
| Workflow edited but not re-published | Old behaviour in the demo | Publish after every change you want live |
| Lovable edited but not re-published | Demo URL shows the old UI | Publish → Publish changes |
| RLS without policies | Insert error, or empty lists; Realtime silent | Policies for `anon`/`authenticated`; test as anon → [[Rules/RLS - test inserts as anon]] |
| `insert().select()` without SELECT policy | Insert "fails" although the row was written | Add a SELECT policy or drop `.select()` |
| Secret key in frontend | Anyone can read or delete all data | Only publishable keys in `VITE_*` → [[Rules/Never put service keys in frontend]] |
| Realtime not enabled on the table | UI never updates | `alter publication supabase_realtime add table …` |
| DB webhook fires on own updates → loops | n8n runs repeatedly | Trigger on INSERT only, or `when (NEW.status='new')` |
| Browser → n8n CORS | `No 'Access-Control-Allow-Origin'` error | Use pattern (a); or a single origin in *Allowed Origins* |
| Lovable Cloud chosen by accident | No secret key for n8n | Decide before the first prompt → [[Rules/Decide Lovable backend before first prompt]] |
| Lovable regenerates code and wipes manual edits | Hand fixes vanish | Put rules in Knowledge; commit and pull often; keep custom logic in n8n or the relay, not in the Lovable code |
